# Legacy URL migration — trucksleon.com

Inventory of the previous website and the redirect map that preserves its SEO.

**Audited 2026-09-28 against the live site.** Every path below was requested
directly; the status column is what the old server actually returned, not an
assumption. Nothing here is guessed from a naming pattern.

Implemented in `src/config/legacy-redirects.ts`, applied by `redirects()` in
`next.config.ts`.

---

## How the inventory was built

1. `https://trucksleon.com/robots.txt` — read; it names a sitemap.
2. `https://trucksleon.com/sitemap.xml` — 6 URLs, two of which appear nowhere
   in the site's own navigation (`/servicios`, `/transparencia-de-ia`).
3. Every internal link on `/`, `/catalogo`, `/blogs` and `/servicios`, captured
   verbatim from the HTML.
4. An HTTP request per candidate URL to confirm it exists.

The old site is not WordPress; the markup and the `/authenticate?ReturnUrl=…`
links indicate an ASP.NET application with a private area.

## Old robots.txt

Crawl-delay 30s for AhrefsBot and SemrushBot, 10s for everyone else. Disallows
`/Search`, `/zonaprivada/*`, `/transparency-ai` and any URL with a query string
(`/*?`). Declares `https://trucksleon.com/sitemap.xml`.

None of that carries over: the new robots.txt is generated by
`src/app/robots.ts` and is driven by `ALLOW_INDEXING`.

## Facts worth keeping in mind

- **Trailing slashes do not exist on the old site.** `/quienes-somos/` returns
  **404** while `/quienes-somos` returns 200, so there are no slash variants to
  redirect.
- **`/galería`** is linked from `/servicios` but returns **404**. It is a broken
  link on the old site, not a URL anyone can have indexed. No redirect.
- **`/catalogo` is the delivered-vehicle listing**, not a shop. The old main nav
  labels it "VEHÍCULOS ENTREGADOS". This is why it maps to
  `/es/vehiculos-entregados` and not to `/es/vehiculos`.
- **Old slugs contain mistakes** and are reproduced exactly. Correcting them
  would simply fail to match the URLs search engines hold.

## Targets are always Spanish

The old site was Spanish-only, so every legacy URL resolves to `/es/…`,
permanently and identically for every visitor. Geo detection applies to `/`
alone (see `docs/deployment-geoip.md`) and must never influence a permanent
redirect: a crawler asking for `/quienes-somos` has to get the same answer every
time.

## Single hop, always

Next evaluates `redirects()` **before** the locale middleware, so
`/quienes-somos` goes straight to `/es/quienes-somos` (308) rather than chaining
through the middleware's `/quienes-somos` → `/es/quienes-somos` (307).
Verified: every entry below answers 308 and reaches a 200 in exactly one
redirect.

## Loss of granularity — stated plainly

23 of the 33 live legacy URLs (11 categories + 12 vehicles) collapse onto 2
destinations. That is a real reduction: a visitor arriving from a search for
"pezzaioli sba31u" now lands on a listing containing it rather than on its own
page.

It is accepted because the alternative is worse. The new site genuinely has no
per-vehicle or per-category URL, and inventing one that renders the same listing
under 23 addresses would create thin duplicate pages — which costs more in
ranking than the consolidation does.

**If per-vehicle pages are wanted later**, each legacy slug can be pointed at its
own new page by editing `LEGACY_VEHICLES` in `src/config/legacy-redirects.ts`;
the mapping from old slug to vehicle is recorded in the table above precisely so
that stays possible.

## Open decision

**`/transparencia-de-ia`** (200, and listed in the old sitemap) is an AI
transparency page. The new site has no equivalent content, so it currently has
**no redirect and will answer 404**.

Redirecting it to the legal notice or the home page would be a soft 404: the
destination would not contain what the URL promises. The honest options are:

1. Leave it 404 — correct if the page is obsolete. *(current behaviour)*
2. Republish the content on the new site and redirect to it.

This needs a decision from the business; it is not a technical call.

## Note on the old site's contact form

The old form posts to the same page and is protected by Google reCAPTCHA. Its
`Mensaje` textarea was inspected on `/`, `/contacto` and `/servicios`: it is
**empty** in the served HTML, and none of the three pages contains any Cyrillic
or non-Latin text (checked byte by byte in the raw response, not in a rendered
view).

A spam-looking string was reported in that field during an earlier manual
inspection. It could not be reproduced. The likeliest explanation is a form
repopulated from a rejected submission — a transient per-request state, not
persisted content. **No evidence of a compromised site was found**, and none is
claimed.

It does reinforce one rule for the migration: **no dynamic content or form
submission from the old site is carried over.** Only the URL map above crosses.
